# 로드맵 — 어떤 순서로 만드는가

**"다음에 뭘 해야 하나"의 답이 여기 있다.**

이 문서는 달력이 아니라 **의존 순서**다. 일정은 밀리지만 순서는 안 밀린다.

```
STATUS.md                        ROADMAP.md (이 문서)
"지금 P05"   ───────────────▶   P05 절을 연다
"체크 3/4"   ◀───────────────   완료 조건을 가져온 것
```

## 쓰는 법

```
1. STATUS.md 를 연다 → 현재 페이즈를 확인한다
2. 이 문서에서 그 페이즈 절만 읽는다
3. 작업한다
4. 완료 조건을 체크하고 STATUS.md 를 갱신한다
```

**한 번에 한 페이즈만 본다.** 앞에서부터 읽지 않는다.
단, 처음 합류한 팀원은 「전체 그림」과 자기 담당 페이즈를 훑어보면 프로젝트가 어떻게 흘러가는지 알 수 있다.

## 왜 이동이 먼저인가

**나머지 전부가 서버가 가진 플레이어 좌표 위에 얹힌다.**

"플레이어가 피식자에 충분히 가까운가?"를 판정하려면 서버에 플레이어 좌표가 제때 와 있어야 한다.
좌표가 끊기거나 튀면 포식·정화·회피 판정이 전부 흔들린다.

**이동이 늦어지면 다른 1주차 항목을 미루고 이동을 먼저 끝낸다. 반대로 밀지 않는다.**

# P02 — 클라 권위 이동  ═══ 게이트 ═══

```
선행    P01
끝나면  내 물고기가 즉시 반응하고, 남의 물고기가 부드럽게 보인다. 4인 원격 테스트를 열 수 있다
난이도  ★
```

## 왜 하는가

**P01의 대충 붙인 NT를 정식 이동으로 다듬는다.** 이후 모든 판정이 서버가 받은 이 좌표를 쓴다.

> 2026-09-23 이전 계획은 서버 권위 + 예측·재조정(P02~P04, 1주)이었다.
> 네트워크 담당 1명의 일정 위험이 가장 커서 클라 권위로 바꿨다 → [MOTION.md](MOTION.md) 「왜 바꿨나」

## 만들 것

1. **플레이어 프리팹 정식화** — `NetworkTransformReliable`(ClientToServer), Rigidbody 기본 kinematic + 소유자만 Dynamic, 충돌 레이어 → [MOTION.md](MOTION.md) 1절
2. **`PlayerMotor`** (`_Game`, 플레이어 담당) — 소유 클라에서만 동작 → 2절
3. **원격 복제본 비활성화** — Motor 끄기, Rigidbody kinematic → 3절
4. **`NetPlayer.ReportState`** — 소유 클라 HFSM 상태를 서버가 검증 후 `State` SyncVar로 → 3절
5. **서버 → 소유자 통로** — `TargetRpc Respawn` · `TargetRpc ApplyImpulse` 자리만 만든다 → 4절
6. NT 텔레포트 · 버퍼 초기화 API를 **설치한 Mirror 버전에서 확인**하고 적어 둔다

## 완료 조건

- [ ] 원격 Client에서 키를 누른 프레임에 반응한다 (**T16**)
- [ ] 원격 Client 2대가 서로를 볼 때 끊기거나 떨리지 않는다. 손실 2% 포함 (**T18**)
- [ ] 원격 복제본에서 `PlayerMotor`가 돌지 않는다

- [ ] **T16 · T18 · T19 전부 원격 Client에서 PASS**

## ═══ 이 게이트가 무엇인가 ═══

**호스트 화면에서는 전부 저절로 통과한 것처럼 보인다** — 호스트는 서버와 같은 프로세스라 지연이 0이다.

```
호스트에서 테스트      → 전부 잘 돼 보임          ← 함정
원격 Client에서 테스트  → 여기서 진짜가 드러난다
```

| ID | 이름 | 보장 | 실패하면 |
|---|---|---|---|
| **T16** | 즉시 반응 | 내 조작이 **즉시** 반응한다 | 원격에서 Motor가 안 켜졌거나 NT 방향이 ServerToClient다 |
| **T18** | 보간 | 남의 물고기가 **안 떨린다** | 원격에서 Motor·물리가 Transform을 건드린다 |
| **T19** | 서버 판정 | 판정이 **서버의 Transform**으로 이루어진다 | 클라가 보낸 좌표로 거리를 잰다 |

전체 절차와 합격 기준은 [TESTING.md](TESTING.md).

**통과 전에는 4인 원격 테스트를 열지 않는다.**

## 만들 것

1. `NetPlayer.RequestEat` — 포식 요청 경로. **대상 ID만 보내고 거리는 서버 Transform + 허용오차로 잰다**
2. **원자적 포식** — `검증 → 소비 선점 → 허기·성장 반영 → 연출 방송 → Despawn`
3. `NetPlayerVitals` — HP · 허기(0~10 정수) · 성장 레벨 · 행동 불능 · 감속 단계
4. 허기 0 → HP 감소
5. **15초 자동 부활** — 서버 → 소유자 `Respawn` → 소유자 순간이동 + NT 버퍼 초기화 → [MOTION.md](MOTION.md) 4절

- [ ] 4명이 같은 HP · 허기 단계를 본다 (T21 · T34)
- [ ] 허기가 **단계가 바뀔 때만** 전송되는데도 값이 안 어긋난다
- [ ] 부활 직후 **죽은 자리로 튕기지 않고, 남의 화면에서 미끄러지지 않는다** (T33)

## 계약

→ [SPEC.md](SPEC.md) 3.2 · 3.3 · [API.md](API.md) 상태 절

## 자주 터지는 곳

- **선점을 반영보다 먼저** 해야 두 번째 요청이 실패한다. 순서를 바꾸면 둘 다 성장한다
- 검증과 커밋 사이에 `await` / `yield`를 넣으면 그 틈에 두 번째 요청이 들어온다

# 주차 매핑과 인계

로드맵은 순서고, 아래는 **달력 기준 목표**다. 밀리면 순서를 지키고 일정을 조정한다.

| 주차 | 페이즈 | 인계 기준 |
|---|---|---|
| 1 | P00 ~ P02, P05 착수 | **T16 · T18 · T19 원격 Client PASS** → 다인 테스트 개방 |
| 2 | P05 ~ P06 | 4인 세션에서 포식·생존·AI 동작 |
| 3 | P07 | 핵심 루프 완주 · `_Contracts` 분리 완료 |
| 4 | P08 | **처음부터 승리까지 플레이 가능** |
| 5 | P09 | 동일 조건 전후 측정 기록 |
| 6 | P10 | 다른 PC에서 실행되는 빌드 |

## 인계마다 남길 것

```
담당자 / 실제 구현 커밋 / 통과한 테스트 ID / 알려진 제한
```

**서명된 계약과 동작 가능한 구현은 구분한다.**
빈 스텁은 컴파일·목업 전용이며, 동작 인계는 **Host + 원격 Client 합격 후에만** 표시한다.
