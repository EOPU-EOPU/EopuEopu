# 로드맵 — 어떤 순서로 만드는가

**"다음에 뭘 해야 하나"의 답이 여기 있다.**

이 문서는 달력이 아니라 **의존 순서**다. 일정은 밀리지만 순서는 안 밀린다.

```
STATUS.md                        ROADMAP.md (이 문서)
"지금 P03"   ───────────────▶   P03 절을 연다
"체크 3/4"   ◀───────────────   완료 조건을 가져온 것
```

## 쓰는 법

```
1. STATUS.md 를 연다 → 현재 페이즈를 확인한다
2. 이 문서에서 그 페이즈 절만 읽는다
3. 작업한다
4. 완료 조건을 체크하고 STATUS.md 를 갱신한다
```

**한 번에 한 페이즈만 본다.** 앞에서부터 읽지 않는다.
단, 처음 합류한 팀원은 「전체 그림」과 자기 담당 페이즈를 훑어보면 프로젝트가 어떻게 흘러가는지 알 수 있다.

## 왜 이동이 먼저인가

**나머지 전부가 서버 좌표 위에 얹힌다.**

"플레이어가 피식자에 충분히 가까운가?"를 판정하려면 서버가 믿을 수 있는 좌표를 갖고 있어야 한다.
좌표가 흔들리면 포식·정화·회피 판정이 전부 흔들린다.

**이동이 늦어지면 다른 1주차 항목을 미루고 이동을 먼저 끝낸다. 반대로 밀지 않는다.**

## 만들 것

1. **입력 프레임 정의** — `MoveInput` 구조체를 확정한다 (팀원 입력 스크립트가 여기 붙는다)
2. 클라 → 서버 입력 Command
3. 서버가 **고정 스텝**으로 입력 큐를 소비하며 `MoveStep` 실행
4. 서버 → 클라 스냅샷 (`MoveState`)
5. P01에서 붙인 `NetworkTransform` 제거

## 1주차에 미리 박을 계약

**지금 `.cs`가 0개라 공짜다. 나중에 넣으면 팀원 코드까지 깨진다.**

자료구조 정의는 → [MOTION.md](MOTION.md) **1절**

| 넣어야 할 것 | 빼먹으면 |
|---|---|
| `MoveStep`의 **외력 슬롯** (`moveConfig`) | 후순위 낚시바늘을 넣을 때 이동 계약을 다시 깨야 한다 |
| `MoveState.MotionEpoch` | 자동 부활 직후 죽은 자리로 한 번 튕겼다 돌아온다 |
| `MoveState.EffectiveConfig` | 감속 디버프 후 옛 속도로 재생 → 보정 직후 다시 튀어나간다 |
| **유실 틱 = 중립 입력 확정** | 손실 환경에서 서버와 클라가 다른 궤적을 낸다 |

# P03 — 클라 예측과 재조정

```
선행    P02 (서버가 위치를 계산해 내려보내고 있다)
끝나면  내 물고기가 입력 즉시 반응하고, 서버와 어긋나도 튀지 않는다
난이도  ★★★  이 프로젝트에서 가장 어려운 한 곳
```

## 왜 하는가

서버 왕복을 기다리면 조작이 RTT만큼 늦는다. **300ms에서는 게임이 안 된다.**
P02를 직접 해봤으면 이게 이미 체감됐을 것이다.

## 만들 것

1. **예측** — 입력을 보낸 즉시 로컬에서 **같은 `MoveStep`** 적용
2. 미확인 입력을 `seq`와 함께 **상한 있는 버퍼**에 보관
3. **재조정** — 스냅샷 수신 시
   ```
   LastProcessedSeq 이하를 버퍼에서 제거
        ↓
   서버 상태와 "그 시점의 예측 기록"을 비교     ← 현재 위치가 아니다
        ↓
   임계값 초과면 서버 상태로 되감고 남은 입력 재적용
        ↓
   차이는 스냅이 아니라 수 프레임에 걸쳐 흡수
   ```
4. **진단 속성** — `PendingInputCount` · `ReconcileCount` · `LastCorrectionDistance`

## 완료 조건

- [ ] 300ms RTT에서 입력 → 화면 반응이 다음 프레임 (**T16 예측**)
- [ ] 진단 로그 3종이 찍힌다
- [ ] 되돌림이 스냅이 아니라 흡수로 보인다 (**T17 재조정**)
- [ ] 조작된 입력(과대 moveDir · 이상한 dt · seq 역행)이 거부되고 로그가 남는다
- [ ] **원격 Client에서** T16 · T17 PASS

→ [MOTION.md](MOTION.md) 클라 계약 절

## 자주 터지는 곳

- **현재 예측 위치와 비교하면 안 된다.** 그 시점의 기록과 비교한다
- **재시뮬레이션에서 RPC · 사운드 · 포식 판정을 재발생시키면 안 된다.** 이동 계산만 다시 한다
- 서버와 클라의 `MoveStep`이 **조금이라도 다르면** 매 프레임 어긋난다.
  임계값을 만지기 전에 **"두 함수가 같은가"를 먼저 의심한다**
- **호스트에서는 이 경로가 비어 있다.** 호스트 확인만으로 합격 처리하지 않는다

## 진단 속성 없이는 판정할 수 없다

`ReconcileCount`와 `LastCorrectionDistance`가 없으면 "재조정이 잘 되는지"를 눈으로만 판단하게 된다.
**이 두 값은 P03의 산출물이지 나중에 붙이는 편의 기능이 아니다.**

## 완료 조건

## 자주 터지는 곳

- **선점을 반영보다 먼저** 해야 두 번째 요청이 실패한다. 순서를 바꾸면 둘 다 성장한다

- 죽었다고 **오브젝트를 파괴하면** 부활시킬 대상이 없다. Downed 상태로 둔다
