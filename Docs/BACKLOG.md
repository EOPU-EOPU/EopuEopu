# 후순위 — 지금은 안 만든다

**이 문서는 평소에 열지 않는다.**

여기 있는 것들은 **설계가 끝났지만 6주 안에 못 넣기로 한 것**이다. 버린 게 아니라 미룬 거라서,
착수할 때 이 문서만 열면 설계가 그대로 있다.

> **되살리는 방법**
> 1. 여기서 해당 절을 통째로 잘라낸다
> 2. 원래 있던 문서(아래 "원위치" 표시)로 옮긴다
> 3. 관련 테스트 ID를 `TESTING.md` 회귀 표에 되돌린다
> 4. `ROADMAP.md`에 주차를 배정한다

**착수 전에 반드시 확인할 것:** 여기 설계는 전부 **인벤토리가 있던 시절**에 쓰였다.
자원·창고를 되살리지 않고 바늘만 넣는 식이면, 그 절이 인벤토리를 전제하는지 먼저 본다.

# 2. 자원 채집 · 인벤토리 · 공유창고

> **원위치:** `API.md` 1절·5절 · `AUTHORITY.md` 권위 표 · 테스트 T02 T03 T04 T07

## 먼저 읽을 것: `NetInteractable`을 언제 만드나

현재 본문에는 이 베이스가 **없다.** 용례가 "피식자 먹기" 하나뿐이라
`NetPlayer`의 Eat 요청 Command로 처리하고 있다.

`_Net/CLAUDE.md`의 규칙이 이것이다:

> 새 추상화는 **게임 기능 2개 이상**이 같은 걸 필요로 할 때만 만든다.

자원 채집이 돌아오면 용례가 2개가 된다. **그때 `NetPlayer`의 Eat 경로와 공통부분을 뽑아
`NetInteractable`로 추출한다.** 미리 만들지 않는다.

## `NetInteractable` — 순간 상호작용

```csharp
public abstract class NetInteractable : NetworkBehaviour
{
    [SerializeField] protected float interactRange = 3f;
    [SerializeField] protected float cooldown = 0.5f;
    protected virtual bool CanInteract(NetPlayer player) => true;
    protected abstract bool OnServerInteract(NetPlayer player); // 거래 성공 시 true
    protected virtual void OnClientResult(NetPlayer player, bool accepted) { }
    public void RequestInteract();
    public bool IsLocalPlayerInRange { get; }
}
```

`CanInteract`는 **부수 효과 없이** 게임 조건만 검사한다. 베이스가 서버 거리·상태·요청 빈도를 추가 검사한다.

`OnClientResult`는 **요청자에게만** 가는 응답이다. 성공 연출의 방송 용도로 쓰지 않는다.
대상이 사라지면 이 훅에 의존하지 말고 플레이어/세션의 지속 객체로 응답한다. player가 이미 떠났으면 null일 수 있다.

`OnServerInteract`가 **`bool`을 반환**하는 이유: 인벤토리 추가 등이 실패하면 `false`를 반환하고
상태를 바꾸지 않는다. 베이스는 이 반환값으로 요청자 응답을 결정한다.
`true`인 경우에만 수락 쿨다운을 갱신하고, **거부 요청에도 요청 빈도 제한은 적용한다.**

### 자원 채집의 필수 순서

이 순서를 어기면 같은 자원이 두 번 지급된다.

```
1. 아직 채집되지 않았고 수량·ID·용량이 유효한지 검증
2. 인벤토리 추가 성공을 확인한 후에만 harvested 상태를 확정
   ↑ 이 사이에 await/yield를 넣지 않는다
3. 살아 있는 세션 이벤트 객체가 위치와 FX ID를 담아 성공 연출을 방송
4. 자원 객체를 Despawn
   ↑ 삭제한 객체의 RPC나 결과 훅에서 연출을 보내지 않는다
```

추가 실패 시 노드를 유지한다. 최초 요청자만 보상받고 뒤의 요청자는 거부된다.
지속되는 노드라면 채집 상태를 동기화하여 **늦게 접속한 사람에게도 복원**한다.

### `_Game/`용 예제

```csharp
protected override bool OnServerInteract(NetPlayer player)
{
    if (harvested) return false;
    if (!player.Inventory.Add(itemId, 1)) return false;  // 가방이 꽉 찼으면 상태를 바꾸지 않는다
    harvested = true;                                    // 추가 성공을 확인한 뒤에 확정
    return true;
}
```

## 인벤토리 · 공유창고

```csharp
public class NetPlayerInventory
{
    public int Get(int itemId);
    public bool Add(int itemId, int count);
    public bool TryRemove(int itemId, int count);
}

public class NetSharedStorage
{
    public static NetSharedStorage Instance { get; }
    public int Get(int itemId);
    public bool TryDeposit(NetPlayer from, int itemId, int count);
    public bool TryWithdraw(NetPlayer to, int itemId, int count);
}
```

이것은 **서버의 동기 처리 서비스 계약**이다.
일반 C# 클래스에 Mirror 속성만 붙인다고 실행 제한이 걸리지 않는다.
서버 전용 조건은 네트워크 어댑터와 서비스 진입점에서 확인하고,
**실제 동기화 컨테이너는 `NetworkBehaviour`가 소유한다.**

검증 항목: `count > 0`, 등록된 ID, 오버플로, 잔량, 용량, 플레이어 상태.
실패하면 **양쪽 수량 모두 불변**이다.
개인↔창고 거래는 차감·추가가 모두 가능한지 확인하고 **한 서버 처리 구간에서 커밋**한다.
클라의 입출고 요청은 창고 상호작용 경로로 보내며 대상 거리·권한도 확인한다.
아이템 ID↔에셋은 게임 레지스트리에서 매핑한다.

## `NetEvents`에 되돌릴 멤버

```csharp
public static IReadOnlyDictionary<int, int> StorageSnapshot { get; }
public static IReadOnlyDictionary<int, int> InventorySnapshot { get; }
public static event Action<int, int> StorageChanged;
public static event Action<int, int> InventoryChanged;
```

`SyncDictionary`의 초기 데이터는 변경 콜백만으로 오지 않는다.
**어댑터가 초기 순회해서 캐시를 만들고 `SnapshotChanged`를 올려야 한다.**

# 3. 건설 · 부화 · 산란/기지

> **원위치:** `API.md` 2절 주석 · `AUTHORITY.md` 권위 표 · 테스트 T06 T13

기획서의 **보너스 목표**다 — 안전한 곳에 알을 낳고, 기지를 개선하며, 치어 부화를 관찰한다.

## 건설: 비용은 한 거래로 묶는다

비용이 있는 건설은 **세 가지를 먼저 결정**해야 한다.

| 결정할 것 | 선택지 |
|---|---|
| 차감 시점 | 시작 때 / 진행 중 투입 / 완료 때 |
| 취소하면 | 환불 / 몰수 |
| 진행도는 | 유지 / 감소 / 리셋 |

**자원 차감과 목표 시작은 한 서버 거래로 묶는다.**
다중 아이템 비용도 **전체 성공 아니면 전체 실패**다. 절반만 차감된 상태를 남기지 않는다.

## 부화: `NetObjective`가 아니다

**`NetObjective`는 "플레이어가 붙어 있는 동안 차는" 목표 전용이다.**
알 부화처럼 **사람이 없어도 흘러가는 타이머**는 여기에 억지로 끼우지 않는다.

서버 시작·완료 시각을 가진 **별도 컴포넌트**로 만든다.
공통화는 실제 중복이 2개 이상 확인된 뒤에 결정한다.

타이머는 **매 프레임 남은 시간을 보내지 말고 종료 시각 하나만 동기화**한다.
클라는 `NetworkTime.time` 기준으로 남은 시간을 계산해 표시한다.

# 4. 낚시바늘 — 구속과 자성

> **원위치:** `AUTHORITY.md` "잡힘과 끌려감" 절 · `_Net/CLAUDE.md` 이동 절 · 테스트 T08 T20

**이동을 건드리는 유일한 후순위 항목이다.** 2026-09-23 클라 권위 전환으로 비용이 "큼"에서 "중간"으로 내려갔다.

## 왜 비싼가

"바늘 쪽으로 딸려간다"는 곧 **내 위치가 내 입력과 무관하게 바뀐다**는 뜻이다.
그런데 이동은 **소유 클라 권위**라 서버가 플레이어 Transform을 직접 쓸 수 없다 → [MOTION.md](MOTION.md) 4절

그래서 답은 **소유 클라의 `PlayerMotor`가 끌려가는 동작을 직접 수행**하는 것이다.

## 이미 본문에 해둔 준비

P02에서 **서버 → 소유자 외력 통로**를 미리 만든다.

```csharp
[Server] NetPlayer.ApplyImpulse(Vector3 impulse);   // 소유자 TargetRpc
event    NetPlayer.ImpulseReceived;                 // PlayerMotor가 구독해 속도에 더한다
```

바늘은 이 통로를 넉백과 같이 쓰거나, 구속 모드 전용 SyncVar를 하나 더한다. **Motor 구조는 다시 뜯지 않는다.**

## 구속(Hooked) 상태 계약

서버가 Hooked 상태와 **바늘 netId·부착 오프셋**을 소유한다. SyncVar로 보낸다.

```
진입  서버가 Hooked = true, 바늘 netId 기록
      소유 클라 Motor가 입력을 잠그고 바늘(서버 권위 오브젝트, 보간된 위치) 쪽으로 끌려간다
      서버는 잡힌 플레이어의 상호작용을 막는다
      거리 판정에는 서버가 가진 플레이어 Transform을 쓴다

해제  서버가 Hooked = false
      소유 클라 Motor가 속도를 초기화하고 조작을 재개한다
      위치를 옮겨야 하면 부활과 같은 Respawn 경로(순간이동 + NT 버퍼 초기화)를 쓴다
```

> 소유 클라가 보는 바늘 위치는 **보간된 과거 위치**다. 끌려가는 궤적이 서버의 바늘과 약간 어긋나지만
> 재조정이 없으니 튀지 않는다. 판정은 서버가 서버 좌표로 한다.

행동 불능(Downed)도 **같은 구조**다 — 서버가 상태를 켜고, Motor가 읽어서 입력을 잠근다.

## 허기 연동: 자성 세기

기획서 4쪽 — *"허기 게이지에 따라 낚시바늘 미끼에 자성 세기 달라짐"*

본문에서 허기는 이미 **0~10 정수 단계**로 동기화하고 있다. 그대로 쓰면 된다.

```
자성 구체 반경 = f(10 - 허기단계)

허기 10 (배부름) → 반경 최소, 거의 안 끌림
허기  0 (굶주림) → 반경 최대, 멀리서도 끌려감
```

**끌려감 시작 판정은 서버가 한다.** 서버가 가진 플레이어 좌표와 허기 단계로 판정하고 Hooked를 켠다.

현재 정화는 **`NetObjective` 한 형태**뿐이다 — 붙어 있는 동안 진행도가 찬다.

## 문제

형태가 하나면 **능력 4종이 전부 "진행바가 빨라진다"로 수렴한다.**

```
붕어 능력    → 정화가 빨라진다
잉어 능력    → 정화가 빨라진다
모래무지 능력 → 정화가 빨라진다
참종개 능력  → 정화가 빨라진다
```

배율만 다르고 체감이 같다. 기획서가 말하는 *"서로 다른 특성을 조합한 역할 플레이"* 가 성립하지 않는다.

## 선택지

| | 비용 | 능력 4종이 살아나나 |
|---|---|---|
| **A. 지금 그대로** (`NetObjective` 1종) | 0 | ❌ 배율만 다름 |
| **B. 즉시형 추가** (E 한 번에 오염원 제거) | 작음 — Command 하나 | △ 조금 |
| **C. 운반형 추가** (오염원을 물고 지정 지점까지) | 큼 | ✅ 확실히 |

**C는 권하지 않는다.** "물고 다니는 상태"는 이동 계산에 영향을 주므로 4번 낚시바늘과 같은 문제에 걸린다.

**B를 고르면** `NetInteractable`의 두 번째 용례가 생기므로, 그때 베이스로 추출하면 된다.

## 주의: `CanContribute`로 역할을 나누는 방법의 함정

```csharp
// 이렇게 하면 역할은 생기지만...
protected override bool CanContribute(NetPlayer p)
    => p.FishId == FishId.모래무지;
```

**그 사람이 행동 불능이면 15초, 접속을 끊으면 영영 진행이 막힌다.**
재접속 복구는 범위 밖이라 복구 수단이 없다.

**능력은 "없으면 못 함"이 아니라 "있으면 빠름"으로 설계한다.**
`NetObjective.SpeedFor(n, weightSum)`가 그걸 위한 구조다.

# 부록: 이 문서에 없는 것

아래는 **후순위가 아니라 기획에서 제외**됐다. 되살리려면 새 결정이 필요하다.

| 제외된 것 | 대체된 것 | 결정일 |
|---|---|---|
| 동료 구조 (다른 플레이어가 살리기) | HP 0 → 15초 후 **자동 부활** | 2026-09-21 |
| 전원 사망 시 세션 재시작 | 없음 — **실패 조건 자체가 사라짐** | 2026-09-21 |
| 초대 코드 · 무작위 방 매칭 | IP 직접 입력 | 2026-09-19 |
| 성장에 따른 몸집 변화 | 능력 배율만 상승 | 2026-09-19 |
| 구역별 버프 | 현재 구역 표시만 | 2026-09-19 |

**동료 구조와 재시작을 되살리면** `RoundCoordinator`, `roundEpoch`, 전체 초기화,
`ReviveSession`, lease/heartbeat가 전부 따라온다. 4주차를 통째로 쓴다고 보면 된다.
