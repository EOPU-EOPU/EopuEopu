# 테스트 방법과 합격 기준

이 문서는 **실행 계획**이다. 아직 Unity 빌드를 실행한 적은 없다.

> **호스트는 서버와 클라가 같은 프로세스에 있어 원격 클라와 다른 경로를 탄다.**
> 모든 Command/RPC가 직렬화를 생략한다고 일반화하지 않는다.
> **호스트에서 잘 된다고 합격이 아니다.**

- UI·연출 개발 중에는 **에디터 단독 확인을 허용**한다.
- 네트워크 동작 변경은 **커밋 전 Host + 별도 Client**로 확인한다.
- 문서만 바꾼 경우 문서 검증으로 충분하다.
- 팀 4인 원격 테스트는 **주 2회 고정**하고 빌드/커밋을 통일한다.

## 게이트: T16 · T18 · T19 — P02 통과 조건

**클라 권위 이동(소유 클라 이동 · NT 원격 보간 · 서버 판정)은 4인 원격 테스트의 진입 조건이다.**

번호가 아니라 **각각이 보장하는 것**으로 기억한다.

| ID | 이름 | 보장 | 실패하면 |
|---|---|---|---|
| **T16** | 즉시 반응 | 내 조작이 **즉시** 반응한다 | 키를 눌러도 0.1~0.3초 뒤에 움직인다 |
| **T18** | 보간 | 남의 물고기가 **안 떨린다** | 남이 끊겨 보이거나 지직거린다 |
| **T19** | 서버 판정 | 판정이 **서버의 Transform + 허용오차**로 이루어진다 | 요청에 실린 좌표로 판정하거나, 닿았는데 못 먹는다 |

> **T17(재조정)은 삭제했다**(2026-09-23). 클라 권위라 재조정이 없다.

### 반드시 원격 Client에서 판정한다

```
호스트에서 테스트      → 넷 다 저절로 통과한 것처럼 보인다   ← 함정
원격 Client에서 테스트  → 여기서 진짜가 드러난다
```

호스트는 서버와 **같은 프로세스**라 지연이 0이고, 서버가 보는 호스트 좌표가 늦지도 않다.
**호스트 단독 확인은 합격 근거가 아니다.**

세 항목이 **원격 Client에서 PASS로 기록되기 전에는** 4인 원격 테스트를 열지 않는다.
안 되는 이동 위에 포식·정화·능력을 쌓으면 나중에 전부 다시 맞춰야 한다.

→ [ROADMAP.md](ROADMAP.md) P02 · [MOTION.md](MOTION.md)

## 실행 스크립트

bat 파일 2개로 각각 저장한다. 폴더 배치는 bat 옆 `Build/FishGame.exe`를 가정한다.

> `-mode`와 `-ip`는 Unity/Mirror 기본 옵션이 **아니다.**
> `CoopNetworkManager`의 인자 파서 구현·검증이 선행되어야 한다.
> 잘못된 옵션은 오류 표시 후 종료한다.

```bat
@echo off
rem Host.bat
start "" "%~dp0Build\FishGame.exe" -mode host -screen-fullscreen 0 -screen-width 800 -screen-height 600
```

```bat
@echo off
rem Client.bat
set "IP="
set /p "IP=Host IP (Enter=127.0.0.1): "
if not defined IP set "IP=127.0.0.1"
start "" "%~dp0Build\FishGame.exe" -mode client -ip "%IP%" -screen-fullscreen 0 -screen-width 800 -screen-height 600
```

- **로컬**: Host 먼저 실행 후 `127.0.0.1`로 접속
- **원격**: Tailscale 연결과 접근 정책, 호스트 UDP 포트 및 방화벽을 확인한 뒤 호스트의 Tailscale IP로 접속
- **Steam**: 별도 PC/계정 및 명시적 트랜스포트 선택으로 수행

무료 제공 범위나 4인 이용 자격은 실제 계정 플랜에서 확인한다.

## 지연·손실 시뮬레이션

`NetworkManager`가 실제 사용하는 Transport를 `LatencySimulation`으로 감싸고 wrap 연결을 확인한다.
Multiplex와 중첩할 때 **지연이 중복 적용되지 않도록** 경로를 기록한다.

> ⚠️ **Inspector의 지연이 편도인지 왕복인지 확인한다.**
> RTT 100ms를 편도 100ms로 잘못 설정하지 않는다.
> **입력 지연값과 관측 RTT를 따로 기록한다.**

시험 프로필: 관측 RTT 약 **0 / 100 / 300ms**, 별도로 unreliable 손실 **0 / 2%**.

현재 upstream 구현의 손실 옵션은 **unreliable 채널에 적용된다.**
reliable 패킷 손실·재전송 장애까지 시험했다고 적지 않는다.
**호스트 로컬 클라만으로 지연 효과를 판정하지 않는다.**

## 별도로 돌릴 조건

정해진 주차 없이, 관련 기능이 들어간 뒤 한 번씩 돌린다.

- **프레임률 혼합** — 30/60/144 FPS를 섞어서 4인 플레이
- **호스트 FPS 급락**, 2초 앱 정지 후 복귀
- **원격 이탈**, 호스트 종료
- **같은 피식자 동시 포식** (T24 확장)
- **가능하면 2대 이상의 PC**에서 확인. 에디터 호스트 + 빌드 3개만으로 끝내지 않는다
- **Server Only + 원격 Client** — 호스트가 숨기는 오류를 찾는 진단 실행

## 통과 기준 (목표값 — 아직 측정하지 않음)

| 항목 | 목표 |
|---|---|
| 입력 후 로컬 표시 반응 | **다음 렌더 프레임** |
| 원격 표시 지연 | RTT 100ms에서 **체감상 끊김 없음.** 보간 버퍼 고갈 횟수 기록 |
| 정적 벽 관통 | **0건** |
| 중복 성장·중복 보상 | **0건** |
| 신뢰성 상태 수렴 | 송신이 멈춘 뒤 **1초 안에** 서버와 일치 |

지속 상태 불일치가 있으면 **실패**다.

별도 기록: 대역폭, 서버 틱 P95/P99, GC Alloc, 보간 버퍼 고갈 횟수.

### 대역폭 예산 잡는 법

측정 전에 **대략 얼마나 나올지** 계산해 두면, 실측값이 이상할 때 바로 알아챌 수 있다.

```
엔티티 수 × 스냅샷 크기 × 전송 주기 × 원격 클라 수 = 호스트 송신량

예:  24개 × 80B × 15Hz × 3명 = 86,400 B/s
```

> ⚠️ **이건 산술 예시지 Mirror 실측값이 아니다.**
> 헤더·재전송·스폰·SyncVar·RPC가 전부 빠져 있다.
> **실제 바이트 수는 직렬화 계측으로 확인한다.**

**먼저 4인 전체 관찰로 구현하고, 측정상 필요할 때만 관심 영역 최적화를 추가한다.**
피식자 개체 수가 이 판단의 주 대상이다 (T32).
**스트레스 환경에서는 부드러움보다 상태 무결성과 회복을 우선한다.**

연속 30분 4인 플레이에서 **예외·유령 오브젝트·증가하는 버퍼가 없어야 한다.**

## 로그와 기록

기본 디버그 로그는 **1주차부터** 역할·빌드 ID·연결 수·오류를 남긴다.

**이동 진단도 1주차 대상이다.** 이 값 없이는 T18 · T19를 판정할 수 없다.

```
보간 버퍼 길이와 고갈 횟수      T18
원격에서 PlayerMotor 실행 여부   T18
포식 요청 시 서버 거리 · 허용오차 · 결과     T19
비정상 속도 로그 발생 횟수
```

5주차 HUD는 RTT와 송수신량을 보강한다.
단위(KB 또는 KiB), 집계 구간, 프로세스별/연결별 범위를 명시한다.
**기능별 비중은 별도 계측 없이는 표시하지 않는다.**

### 결과 기록 양식

```
날짜 / 담당 / 커밋 / Unity·Mirror 버전 / PC 및 역할 / 전송 설정
지연 설정 · 관측 RTT
이동 설정 (NT 종류 · 송신 주기 · 보간 버퍼 배수 · 판정 허용오차)
테스트 ID / PASS · FAIL · 미실행 / 로그 · 영상 경로
```

빌드는 exe만이 아니라 **실행에 필요한 전체 폴더**를 배포한다.
