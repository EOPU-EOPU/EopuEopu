# 네트워크 기초 — 아무것도 모른다는 가정에서

이 문서는 **멀티플레이 경험이 전혀 없는 팀원**이 읽는 첫 문서다.
코드를 쓰기 위한 문서가 아니라, 다른 문서에 나오는 말이 **무슨 뜻인지** 알기 위한 문서다.

```
"권위"  "예측"  "재조정"  "보간"  "스냅샷"  "Late Join"
```

이 여섯 단어가 다른 문서 전체에 나온다. 여기서 한 번 잡고 가면 나머지가 읽힌다.

**순서대로 읽는다.** 외울 필요는 없고, 헷갈릴 때 돌아와서 해당 절만 다시 보면 된다.
30분 정도 걸린다.

이 문서에 나오는 수치(20Hz, 0.1m, 100ms 등)는 다른 문서에서 가져온 **측정 전 시작값**이다. 개념을 설명하기 위한 예시로만 읽는다.

> **예시로 나오는 기능이 전부 만들 기능은 아니다.**
> 자원 채집·창고·부화·낚시바늘은 **개념을 설명하기 좋아서** 예시로 남겨 뒀지만,
> 2026-09-21 결정으로 **후순위**다. 동료 구조와 전원 사망 재시작은 **제외**됐다.
> 지금 만들 범위는 [문서 안내](../README.md)를 본다.
> 여기서는 "이런 종류의 문제가 있다"만 가져가면 된다.

## 0. 한 문장 요약

> 멀티플레이는 "화면 4개를 똑같이 맞추는 일"이 아니라, **"진짜는 한 군데에만 있고, 나머지 3개는 그 진짜를 늦게 베껴 그린 그림"** 이라는 사실을 받아들이고 그 위에서 게임을 만드는 일이다.

싱글 게임에서 버그가 나면 "계산이 틀렸다"이다. 멀티에서 버그가 나면 대부분 **"누가 정하는지 안 정했다"** 또는 **"늦게 도착한 걸 고려 안 했다"** 이다. 이 문서의 나머지는 전부 이 두 문장의 부연이다.

---

## 1. 싱글플레이와 뭐가 다른가

싱글 게임은 이렇게 생겼다.

```
[ 내 PC ]
  입력 → 계산 → 화면
```

입력한 순간 계산이 되고, 계산된 순간 화면에 나온다. 사이에 아무것도 없다. `if (hp <= 0) Die();` 라고 쓰면 그게 곧 진실이다.

멀티는 이렇게 생겼다.

```
[ A의 PC ]  입력 → ...(인터넷)... → [ 서버 ] 계산 → ...(인터넷)... → [ A,B,C,D의 화면 ]
```

중간에 **인터넷**이 두 번 낀다. 인터넷은 느리고(수십~수백 ms), 가끔 데이터를 흘리고, 순서를 바꾸기도 한다. 그래서 싱글에서는 존재하지 않던 질문이 생긴다.

- 이 계산은 **누구 PC에서** 하나?
- 계산 결과를 **언제** 다른 사람에게 알리나?
- 알림이 **아직 안 왔을 때** 화면에 뭘 그리나?
- 알림이 **영영 안 오면** 어떻게 되나?

이 4개 질문에 답하는 게 네트워크 작업의 전부다.

## 2. 서버와 클라이언트, 그리고 호스트

### 서버 (Server)
"진짜 게임"이 돌아가는 곳. 물고기가 실제로 어디 있는지, 오염도가 몇 %인지, 누가 쓰러졌는지를 **결정하고 보관하는 단 하나의 장소**.

### 클라이언트 (Client, 줄여서 클라)
플레이어가 실제로 보는 화면. 서버가 알려준 내용을 **받아서 그린다**. 클라가 스스로 정하는 건 원칙적으로 없다(카메라·UI·이펙트 같은 "나만 보는 것" 제외).

### 호스트 (Host) ← **우리 프로젝트가 쓰는 방식**
서버와 클라를 **한 PC에서 동시에** 돌리는 것. 방을 만든 사람이 곧 서버다. 별도 서버 컴퓨터를 빌리지 않아도 된다.

```
     [ 방장 PC ]                [ 친구1 ]   [ 친구2 ]   [ 친구3 ]
   ┌──────────────┐
   │  서버 (진짜)  │ ←──────────── 클라       클라       클라
   │      ↕       │
   │  클라 (화면)  │
   └──────────────┘
```

**호스트에서 제일 조심할 것:** 방장 PC에서는 서버와 클라가 같은 메모리를 쓰기 때문에 **인터넷 지연이 0이다.** 그래서 네트워크 버그가 방장 화면에서는 안 보인다. "내 화면에선 잘 되는데요"의 90%가 이것이다.

> 그래서 규칙: **호스트 화면만 보고 "된다"고 하지 않는다.** 반드시 별도 PC(또는 별도 빌드)의 클라이언트에서 확인한다. → [테스트 표](../TESTING.md)

## 3. 권위(Authority) — 이 문서 전체에서 제일 중요한 단어

**권위 = "이 값을 진짜로 정하는 사람이 누구인가"**

예를 들어 "물고기 A의 위치"에 대해 권위가 서버에 있다면:
- 서버가 정한 위치가 진짜다.
- 클라가 "나 여기 있어요"라고 말해도 서버는 **참고만 하거나 아예 무시**한다.
- 모든 판정(바늘에 닿았나? 자원에 닿았나?)은 **서버가 가진 좌표로만** 한다.

### 왜 서버가 정해야 하나

권위를 클라에 주면 이런 일이 생긴다.

| 클라가 정하게 두면 | 실제로 벌어지는 일 |
|---|---|
| 클라가 "내 위치는 여기" | 조작하면 순간이동·벽 통과가 그냥 된다 |
| 클라가 "자원 5개 먹었음" | 숫자만 바꾸면 무한 자원 |
| 클라가 "정화 100% 끝" | 4명이 각자 다른 시점에 끝났다고 주장 → 화면이 서로 다름 |

마지막 줄이 핵심이다. **치트 방지보다 "4명의 화면이 안 갈라지게 하는 것"이 더 큰 이유다.** 우리는 PvP가 없어서 치트 동기는 적지만, 화면이 갈라지면 게임이 그냥 망가진다.

### 우리 프로젝트의 권위 배분

**전부 서버 권위다.** 이동도 포함한다. 자세한 표는 [권위 분배](../SPEC.md)에 있다.

클라가 혼자 정해도 되는 건 **"나만 보는 것"** 뿐이다: 카메라 각도, UI 열림/닫힘, 로컬 이펙트, 사운드, 페이드.

> 구분하는 법: **"이게 틀리면 다른 사람 화면도 틀리나?"** → 그렇다면 서버 권위. 아니라면 로컬.

## 4. 지연(Latency)과 그로 인한 근본 문제

### RTT (Round Trip Time, 왕복 지연)
내가 보낸 게 서버에 갔다가 답이 돌아오기까지 걸린 시간. 국내 30~60ms, 해외 150~300ms 정도.

### 여기서 생기는 딜레마

이동을 서버가 정한다고 하자. 그러면 순서가 이렇다.

```
0ms    W키 누름
       ↓ (인터넷, 30ms)
30ms   서버가 받아서 계산
       ↓ (인터넷, 30ms)
60ms   내 화면에서 물고기가 드디어 움직임
```

**키를 누르고 60ms 뒤에 움직인다.** 이건 사람이 명확히 느낀다. "조작이 무겁다", "물속에서 움직이는 것 같다"(하필 물고기 게임이지만 이건 나쁜 의미다).

그렇다고 클라가 정하게 하면 3장의 문제가 터진다. 그래서 둘 다 한다. 이게 다음 절이다.

## 5. 예측 · 재조정 · 보간 — 3종 세트

**우리 프로젝트의 1주차 필수 항목**이다. 이름이 어려워서 그렇지, 시작점은 딱 하나다.

### 5-0. 먼저 이것부터 — 화면의 물고기는 두 종류다

내 화면에 물고기가 4마리 떠 있다. 이 4마리는 **성격이 완전히 다른 두 부류**다.

```
┌──────────────── 내 화면 ────────────────┐
│                                         │
│   🐟 내 물고기 1마리                     │
│      · 내가 키보드로 조종한다             │
│      · 내가 무슨 입력을 넣었는지 안다      │
│                                         │
│   🐠🐠🐠 남의 물고기 3마리               │
│      · 쟤들이 뭘 누르는지 나는 모른다      │
│      · 서버가 알려주는 위치만 받는다       │
│                                         │
└─────────────────────────────────────────┘
```

이 둘은 **겪는 문제가 다르고, 그래서 해법도 다르다.**

| | 내 물고기 | 남의 물고기 |
|---|---|---|
| 겪는 문제 | 서버 답을 기다리면 **조작이 굼뜨다** | 위치가 **띄엄띄엄** 온다 (초당 20번) |
| 그래서 | 미리 계산해서 먼저 그린다 → **예측** | 받은 점 사이를 이어 그린다 → **보간** |
| 부작용 | 미리 계산한 게 틀릴 수 있다 → **재조정** | (없음) |

**즉, 3종 세트는 "3단계"가 아니라 이렇게 갈린다.**

```
내 물고기   →  예측  →(틀렸으면)→  재조정
남의 물고기 →  보간
```

재조정은 예측의 뒤처리이고, 보간은 아예 다른 대상에 쓰는 다른 기술이다. **이 둘은 순서 관계가 아니다.** 혼동되는 건 대개 여기서 시작한다.

### 5-1. 예측 (Prediction) — 내 물고기: "일단 내가 먼저 그려놓기"

서버 답을 기다리면 키 누르고 60ms 뒤에 움직인다(4장). 그래서 **기다리지 않는다.**

```
0ms   W키 → ① 서버로 입력 전송
             ② 동시에 내 화면에서 그냥 움직여버림   ← 조작감 살아남
60ms  서버 답 도착 → 내가 미리 그린 것과 비교
```

**미리 그린 게 맞을 거라고 믿는 근거:** 서버와 내 PC가 **똑같은 이동 계산 함수**를 쓴다. 같은 입력 → 같은 함수 → 같은 결과. 그래서 평소엔 거의 항상 맞는다.

> 그래서 규칙: 이동 계산은 **`MoveStep` 한 곳에만** 둔다. 서버용/클라용을 따로 만들면 결과가 갈라지고, 그 순간 예측이 통째로 망가진다. 이 함수 안에서 난수·`Time.time`·프레임률 의존 값을 못 쓰게 하는 것도 같은 이유다 — 그런 게 들어가면 같은 입력에도 다른 답이 나온다.

### 5-2. 재조정 (Reconciliation) — 내 물고기: "틀렸으면 고쳐 쓰기"

예측이 늘 맞지는 않는다. 서버가 다르게 판단할 수 있다. "거기 벽이야", "너 바늘에 잡혔어", "속도 상한 넘었어."

**한 줄로:** 재조정 = **내가 미리 그려둔 위치를, 나중에 도착한 서버의 정답에 맞춰 고치는 일.**

비유하면 **받아쓰기 채점**이다. 일단 내 귀로 듣고 먼저 다 적어둔다(예측). 나중에 정답지가 온다(서버 스냅샷). 틀린 데를 고친다(재조정).

그런데 고칠 때 두 가지가 걸린다.

#### 걸림돌 1 — 정답지가 늦게 온다

서버 답은 **60ms 전 상태**다. 그 사이 나는 키를 더 눌렀다. 서버 위치로 그냥 덮어쓰면 **그 사이 입력이 통째로 사라진다.** (= 앞으로 가고 있는데 갑자기 뒤로 끌려가는 느낌)

그래서 입력마다 번호(seq)를 붙여서 보관해뒀다가, 이렇게 한다.

```
내 입력 보관함:   [#10][#11][#12][#13]     ← #12, #13은 아직 서버가 모름

① 서버: "#11까지 처리했고, 그 결과 위치는 P다"
② #11 이하는 이제 확정됐으니 버린다  →  [#12][#13]
③ 내 위치를 P로 되돌린다              →  (#11 시점으로 되감기)
④ 남은 #12, #13을 P 위에 다시 계산한다 →  최신 입력이 안 날아감 ✔
```

이게 "되감아서 다시 계산"의 전부다. 되감는 이유는 **틀려서**가 아니라, 서버 답이 과거 것이라 **그 이후를 다시 쌓아 올려야** 하기 때문이다.

#### 걸림돌 2 — 고친 걸 화면에 옮기면 눈에 띈다

③④를 거쳐 "올바른 위치"가 나왔다. 이제 화면의 물고기를 거기로 옮겨야 하는데, 방법이 둘이다.

**스냅(snap) = 이번 프레임에 곧바로 그 위치로 옮긴다.**
정확하다. 대신 거리가 멀면 **순간이동으로 보인다.** 이게 "화면이 튄다"의 정체다.

**흡수 = 여러 프레임에 걸쳐 조금씩 옮긴다.**
예를 들어 0.06m 어긋났으면, 한 번에 옮기지 않고 0.1초 동안 프레임마다 나눠 옮긴다. 플레이어는 보정이 일어난 줄도 모른다. 대신 그 0.1초 동안 화면은 **살짝 틀린 위치**를 보여준다.

```
0.06m 어긋난 걸 화면에 반영하는 두 방법

스냅:  0.06m ──────▶ 0                     (1프레임. 정확 / 눈에 띔)
흡수:  0.06 → 0.04 → 0.02 → 0.01 → 0       (0.1초. 안 보임 / 잠깐 부정확)
```

**어긋난 거리에 따라 고른다.**

| 어긋난 거리 (시작값) | 처리 | 왜 |
|---|---|---|
| 0.1m 미만 | 되감지 않고 **흡수만** | 이 정도는 정상 오차. 매번 되감고 스냅하면 화면이 계속 잘게 떤다 |
| 0.1m ~ 2m | **되감기+재계산** 후 결과를 **흡수**로 반영 | 진짜 예측이 틀린 경우. 고치되 티 안 나게 |
| 2m 이상 | 즉시 **스냅** + **로그** | 순간이동 수준이라 흡수로 감출 수 없다. 게다가 대개 **버그 신호**라 기록을 남겨야 한다 |

한 줄 요약: **작으면 몰래 맞추고, 크면 티 나게라도 정확히 맞추고 기록을 남긴다.**

> **"이동이 튄다 / 뒤로 끌려간다"는 증상은 거의 항상 여기다.** 임계값(0.1m)이나 흡수 시간(0.1초)을 건드리기 전에 먼저 **"서버와 클라의 이동 함수가 달라졌나?"** 를 의심한다. 두 함수가 다르면 매 프레임 어긋나므로 임계값을 아무리 만져도 해결되지 않는다.

### 5-3. 보간 (Interpolation) — 남의 물고기: "점 사이를 이어 그리기"

여기서 대상이 바뀐다. 남의 물고기·포식자·바늘 얘기다.

남의 물고기는 **예측할 수가 없다.** 쟤가 W를 누를지 S를 누를지 내가 모르기 때문이다. 그러니 서버가 보내주는 위치를 받아 그리는 수밖에 없다. 문제는 그게 **초당 20번밖에 안 온다**는 것.

```
서버가 보낸 것:   ●         ●         ●         ●     (50ms마다 1개)
그대로 그리면:    뚝    뚝    뚝    뚝              ← 순간이동하듯 끊김
보간해서 그리면:  ●─────────●─────────●─────────●     ← 부드러움
```

**한 줄로:** 보간 = **띄엄띄엄 받은 위치 사이를 채워서 부드럽게 그리는 일.**

여기엔 대가가 하나 있다. "점과 점 사이"를 그리려면 **뒤쪽 점이 이미 도착해 있어야** 한다. 그래서 일부러 **조금 과거를 그린다**(시작값 100ms). 남의 물고기는 항상 살짝 과거 모습이다 — 버그가 아니라 설계다.

> 그래서 규칙: **남의 물고기에서 이동 함수를 다시 돌리지 않는다.** 남의 것은 "계산할 대상"이 아니라 "받아서 그릴 대상"이다. 여기서 이동 계산을 돌리면 내가 계산한 위치와 서버가 보낸 위치가 서로 잡아당겨 미끄러지거나 떤다.

### 5-4. 재조정 vs 보간 — 뭐가 다른가

제일 많이 헷갈리는 지점이라 따로 정리한다.

| | **재조정** | **보간** |
|---|---|---|
| **누구한테** | 내 물고기 | 남의 물고기·포식자·바늘 |
| **무슨 문제를 푸나** | 내가 미리 계산한 게 서버와 다를 수 있다 | 위치가 띄엄띄엄 와서 끊겨 보인다 |
| **하는 일** | 틀린 걸 **고친다** | 빈 곳을 **채운다** |
| **이동 함수를** | 다시 돌린다 (되감고 재계산) | **안 돌린다** (받은 값만 씀) |
| **없으면** | 벽을 뚫거나 서버와 위치가 영영 어긋남 | 남의 물고기가 뚝뚝 끊겨 보임 |
| **비유** | 받아쓰기 채점하고 고쳐 쓰기 | 띄엄띄엄 찍힌 점 이어서 선 그리기 |

**가장 중요한 차이 한 줄:** 재조정은 **계산을 다시 하는 것**, 보간은 **계산 없이 그리기만 하는 것**.

### 3종 세트 정리

| 대상 | 방식 | 이유 |
|---|---|---|
| 내 물고기 | 예측 + 재조정 | 즉각 반응이 필요하고, 내 입력은 내가 아니까 미리 계산할 수 있다 |
| 남의 물고기 / 포식자 / 바늘 | 보간만 | 남의 입력을 모르니 예측 불가. 부드럽게 그리기만 하면 된다 |

## 6. 상태 동기화 vs 이벤트 — 헷갈리면 가장 자주 깨지는 곳

서버가 클라에게 뭔가 알리는 방식은 크게 둘이다.

### 상태(State) 동기화 — "지금 값은 7이다"
- 값이 바뀔 때마다 새 값이 전달된다.
- **나중에 들어온 사람도 현재 값을 받는다.**
- 예: 오염도, 정화 진행도, HP, 허기 단계, 생존 여부, 위치

### 이벤트(Event) / 일회성 RPC — "방금 폭발이 일어났다"
- 그 순간 접속해 있던 사람에게만 한 번 간다.
- **지나가면 사라진다. 나중에 들어온 사람은 모른다.**
- 예: 이펙트 재생, 효과음, "정화 완료!" 팝업

### 그래서 생기는 대표 버그

> UI를 이벤트만 구독해서 만들었다. → 게임 중간에 UI를 열면 **오염도가 100%로 보인다.**
> 이미 60%까지 내려갔는데, 지나간 "오염도 변경 이벤트"를 못 들었기 때문이다.

**해결:** UI는 **구독(앞으로의 변경) + 현재 스냅샷 읽기(지금까지의 결과)를 둘 다** 한다.
이건 UI 담당이 특히 자주 밟는 지뢰다.

```csharp
void OnEnable()
{
    NetEvents.PollutionChanged += Redraw;   // 앞으로의 변경
    Redraw(NetEvents.Pollution01);          // 지금 상태  ← 이거 빼먹으면 버그
}
void OnDisable()
{
    NetEvents.PollutionChanged -= Redraw;   // 해제 안 하면 누수 + 중복 호출
}
```

같은 이유로, 늦게 들어온 사람(Late Join)이나 멀리 있다 돌아온 경우에도 **"현재 상태"로 복원**되어야 한다. 지나간 이벤트를 다시 받을 거라 기대하면 안 된다.

## 7. 오브젝트 생성과 삭제 — `Instantiate`가 금지인 이유

싱글에서는 `Instantiate(prefab)` 하면 끝이다. 멀티에서는 **그 오브젝트가 내 PC에만 생긴다.**

```
나:   자원 아이템 생성됨 ●     "먹었다!"
친구: 아무것도 없음            "쟤 왜 저러지?"
```

이걸 **유령 오브젝트**라 부른다. 삭제도 마찬가지로, 내 화면에서만 사라지고 남들에겐 계속 있다.

**해결:** 공유되어야 하는 오브젝트는 **서버가** `NetSpawner.Spawn`으로 만든다. 그러면 서버가 모든 클라에게 "이거 만들어라"고 알려준다. 삭제도 `NetSpawner.Despawn`.

| 만드는 것 | 방법 |
|---|---|
| 자원 아이템, 바늘, 물고기, 건설물 (= 모두가 봐야 함) | 서버에서 `NetSpawner.Spawn` |
| 물보라 파티클, 데미지 숫자, UI 팝업 (= 나만 봄) | `Instantiate` 그대로 OK |

판단 기준은 3장과 같다: **"남의 화면에도 있어야 하나?"**

## 8. 시간 — `Time.time`이 금지인 이유

`Time.time`은 **그 PC가 켜진 뒤 흐른 시간**이다. 4명이 서로 다른 시각에 게임을 켰으니 4명의 `Time.time`은 전부 다르다.

```
A의 Time.time = 312.4
B의 Time.time =  87.1
C의 Time.time = 1044.9
```

이 값으로 "30초 뒤에 부화 완료"를 각자 계산하면 **4명이 다 다른 시점에 부화한다.**

**해결 두 가지:**

1. **서버가 판정한다.** 부화 완료 여부는 서버가 정하고 상태로 내려보낸다. (원칙)
2. **표시는 공유 시각 기준으로 한다.** 서버가 "완료 시각 = 1523.0(서버 시간)"을 내려주면, 각 클라는 `NetworkTime.time`(모두가 대략 일치하도록 맞춰진 공유 시계)으로 남은 시간을 계산해 표시한다.

**여전히 `Time.time` / `Time.deltaTime`을 써도 되는 곳:** UI 페이드, 트윈, 카메라 흔들림 같은 순수 로컬 연출. 이건 각자 달라도 아무 문제 없다.

> 구분: **"이 시간으로 무언가를 결정하나, 아니면 그냥 보여주나?"** 결정하면 서버/`NetworkTime`, 보여주기만 하면 `Time.time` 가능.

## 9. `static`에 게임 상태를 넣으면 안 되는 이유

`static int totalResource = 0;` 이라고 쓰면, 이 변수는 **각 PC에 하나씩, 총 4개가 따로 존재한다.** 하나의 공유 변수가 아니다. 네트워크는 `static`을 통해 흐르지 않는다.

```
A의 totalResource = 5
B의 totalResource = 0   ← A가 먹은 걸 모름
```

**해결:** 공유 수치는 서버가 가지고 동기화 변수로 내려보낸다.

**예외:** 값을 보관하지 않고 **찾아가기만 하는** static은 괜찮다. `NetEvents.LocalPlayer` 같은 것. 이건 "내 플레이어가 누구냐"를 알려줄 뿐 게임 진행 수치를 들고 있지 않다.

---

## 10. "내 캐릭터"를 구분하는 법

한 화면에 물고기가 4마리 있다. 그중 **하나만 내 것**이다. 입력을 처리하기 전에 반드시 확인해야 한다.

```csharp
void Update()
{
    var player = NetEvents.LocalPlayer;
    if (player == null || !player.IsMine) return;  // 이 줄이 없으면 4마리가 다 움직인다
    // 여기서부터 내 입력 처리
}
```

`player == null` 검사가 붙어 있는 이유: **접속 직후에는 내 플레이어가 아직 안 만들어져 있다.** 네트워크 게임에서는 "아직 준비 안 된 상태"가 항상 존재하고, 싱글과 달리 이게 몇 프레임~몇 초 지속될 수 있다.

또한 **`FindObjectOfType<NetPlayer>()`를 쓰면 안 된다.** 남의 물고기가 잡힌다. 반드시 지정된 조회 경로(`NetEvents.LocalPlayer` 등)를 쓴다.

## 11. 서버는 클라를 믿지 않는다

클라가 보내는 요청은 전부 **"부탁"이지 "통보"가 아니다.** 서버는 받을 때마다 확인한다.

| 확인할 것 | 예 |
|---|---|
| 보낸 사람이 맞나 | 남의 인벤토리를 건드리려는 요청인가 |
| 상태가 맞나 | 죽었거나 바늘에 잡힌 상태에서 채집 요청이 왔나 |
| 거리가 맞나 | 30m 떨어진 자원을 먹겠다고 하나 |
| 값이 말이 되나 | 수량이 음수인가, 방향 벡터가 NaN인가, 상한을 넘나 |
| 너무 자주 오나 | 1초에 1000번 요청이 오나 |

이동 입력도 예외가 아니다. 입력 번호(seq)가 거꾸로 가거나 중복인지, 클라가 보낸 `dt`가 비정상적으로 크지 않은지(→ 서버는 **자기 시간을 쓰고** 클라 dt를 신뢰하지 않는다), 방향 값이 정규화되어 있는지를 본다.

> 우리는 본격적인 안티치트는 범위 밖이지만, **"말이 안 되는 요청은 거부한다"는 기본 방어는 포함**한다. 이건 치트 대응이라기보다 버그 대응에 가깝다 — 실제로는 조작보다 우리 코드 버그가 이상한 값을 훨씬 자주 보낸다.

## 12. 물리를 쓰지 않는 이유

`Rigidbody.AddForce`로 물고기를 움직이면 이렇게 된다.

- 물리 엔진이 프레임마다 위치를 바꾼다.
- 동시에 서버 스냅샷도 위치를 바꾸려 한다.
- **둘이 서로 다른 위치로 잡아당긴다.** 물고기가 떨거나 미끄러진다.

게다가 물리는 프레임률·부동소수점 차이에 민감해서, 서버와 클라에서 **같은 입력에 같은 결과가 나온다는 보장이 없다.** 그러면 5-1의 예측이 성립하지 않는다.

**그래서:** `isKinematic = true`(물리 엔진이 건드리지 않음) + 중력 끔 + 우리가 직접 속도를 계산해 `MovePosition`으로 옮긴다. 충돌 감지는 여전히 쓰되, 움직임은 우리가 전적으로 통제한다.

## 13. 용어 사전

| 용어 | 뜻 | 쉽게 |
|---|---|---|
| **서버 / 클라이언트** | 진짜를 정하는 쪽 / 받아서 그리는 쪽 | 원본 / 복사본 |
| **호스트** | 서버+클라를 한 PC에서 | 방장이 심판 겸 선수 |
| **권위(Authority)** | 그 값을 정할 자격 | "누가 정하냐" |
| **소유 클라(Owner)** | 그 오브젝트를 조종하는 클라 | "내 물고기" |
| **원격 복제본(Remote)** | 남의 오브젝트가 내 화면에 그려진 것 | 남의 물고기 |
| **RTT / 핑** | 왕복 지연 시간 | 답 오는 데 걸리는 시간 |
| **Hz / Tick Rate** | 초당 몇 번 보내나 | 20Hz = 초당 20번 |
| **스냅샷(Snapshot)** | 어느 시점의 상태 묶음 | 서버가 찍어 보낸 사진 |
| **예측(Prediction)** | **내 것**을, 서버 답 전에 내가 먼저 계산 | 미리 그려두기 |
| **재조정(Reconciliation)** | **내 것**을, 서버 답에 맞춰 되감아 다시 계산 | 채점 후 고쳐 쓰기 |
| **스냅(Snap)** | 고친 위치로 이번 프레임에 곧바로 옮김 | 한 번에 확 옮기기 |
| **흡수(Smoothing)** | 고친 위치로 여러 프레임에 걸쳐 조금씩 옮김 | 티 안 나게 슬쩍 맞추기 |
| **보간(Interpolation)** | **남의 것**을, 받은 점 사이를 채워 그림 (계산 안 함) | 점 잇기 |
| **외삽(Extrapolation)** | 다음 점이 안 왔을 때 추측해서 연장 | 찍기 (짧게만) |
| **SyncVar** | 서버가 바꾸면 클라로 자동 전달되는 변수 | 자동 공유 변수 |
| **Command** | 클라 → 서버 요청 | "해주세요" |
| **RPC** | 서버 → 클라 호출 | "이거 해라" |
| **Spawn / Despawn** | 모두의 화면에 생성/삭제 | 공유 생성/삭제 |
| **Late Join** | 게임 도중 참가 | 늦게 들어옴 |
| **Kinematic** | 물리 엔진이 안 건드리는 Rigidbody | 손으로 옮기는 물체 |
| **결정론적(Deterministic)** | 같은 입력이면 항상 같은 결과 | 재현 가능 |

## 14. 증상 → 원인 빠른 표

| 증상 | 먼저 의심할 것 |
|---|---|
| 내 화면에만 오브젝트가 있다 | `Instantiate`를 클라에서 호출 (7장) |
| 내 물고기가 계속 튄다 / 뒤로 끌려간다 | 서버와 클라의 이동 함수가 다름 (5-2) |
| 남의 물고기가 뚝뚝 끊긴다 | 보간이 없음 (5-3) |
| 남의 물고기가 미끄러지거나 떤다 | 원격 복제본에서 이동 계산을 또 돌림 (5-3) |
| UI를 나중에 열면 값이 0이다 | 이벤트만 구독, 현재 상태를 안 읽음 (6장) |
| 4명이 서로 다른 시각에 완료된다 | `Time.time`으로 판정 (8장) |
| 값이 나만 올라간다 | `static`에 게임 상태 보관 (9장) |
| 4마리가 동시에 움직인다 | `IsMine` 검사 누락 (10장) |
| 방장 화면에선 되는데 친구 화면에선 안 된다 | 호스트는 지연이 0이라 안 드러난 것 (2장) |
| 재접속/재진입하면 상태가 비어 있다 | 일회성 이벤트에 의존 (6장) |

## 15. 습관 3가지

작업하면서 매번 물어볼 질문이다. 이거 셋만 해도 대부분 막힌다.

1. **"이게 틀리면 남의 화면도 틀리나?"** → 그렇다면 서버가 정해야 한다.
2. **"나중에 들어온 사람도 이걸 알 수 있나?"** → 이벤트가 아니라 상태로 만든다.
3. **"호스트가 아닌 진짜 클라에서 확인했나?"** → 안 했으면 아직 확인한 게 아니다.
