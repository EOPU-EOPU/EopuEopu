# 이동 계약

**네트워크 담당이 1주차 내내 보는 문서다.**

이동은 **서버 권위**다. 클라는 좌표가 아니라 **입력**을 보내고,
소유 클라만 같은 함수를 로컬에서 미리 돌려 즉시 반응하며(예측),
서버 스냅샷과 어긋나면 되감아 다시 적용한다(재조정).
내 것이 아닌 대상은 스냅샷 사이를 **보간**해 표시한다.

> **왜 이렇게 하는지**가 궁금하면 [LEARN/01_CONCEPTS.md](LEARN/01_CONCEPTS.md)를 먼저 읽는다.
> 이 문서는 "어떻게 만드는가"만 다룬다.
>
> **어떤 순서로 만드는지**는 [ROADMAP.md](ROADMAP.md) P02~P04.

## 세 가지가 각각 무엇을 고치는가

```
서버 시뮬레이션   좌표를 한 곳에서만 정한다        → 판정이 흔들리지 않는다
예측 + 재조정     내 화면이 즉시 반응한다          → 300ms에서도 조작된다
원격 보간         남의 물고기가 안 떨린다          → 보기에 부드럽다
```

**셋은 세트다.** 하나만 빼면 나머지가 성립하지 않는다.

# 1. 자료구조

```csharp
public struct MoveInput            // 클라 → 서버
{
    public uint       Seq;          // 연결별 단조 증가
    public uint       TargetTick;   // 이 입력이 소비될 서버 틱
    public uint       MotionEpoch;  // 부활·순간이동 이력 구분
    public float      DeltaTime;    // 참고용. 서버는 신뢰하지 않고 클램프한다
    public Vector3    MoveDir;      // 정규화된 방향. 크기는 서버가 강제
    public Quaternion LookRot;
    public uint       Buttons;
}

public struct MoveConfig           // 이동 계산에 들어가는 서버 확정 계수
{
    public uint  Revision;         // 오래된 값 판별용
    public float SpeedMul;         // 감속 디버프 등
    // 후순위: 바늘 인력 벡터·자성 반경이 여기 들어온다
}

public struct MoveState            // 서버 → 클라 스냅샷
{
    public uint       LastProcessedSeq;  // 이 seq까지 서버가 반영함
    public uint       MotionEpoch;       // 부활 시 증가
    public Vector3    Position;
    public Quaternion Rotation;
    public Vector3    Velocity;
    public MoveConfig EffectiveConfig;   // 서버가 확정한 계수를 같이 보낸다
    public double     ServerTime;        // NetworkTime 기준
}

public static class MoveStep       // 서버와 소유 클라가 같은 코드를 사용
{
    public static MoveState Step(MoveState state, MoveInput input, MoveConfig config, float dt);
}

public class NetPlayerMotor : NetworkBehaviour
{
    [SerializeField] float inputSendRate      = 30f;   // Hz
    [SerializeField] float snapshotSendRate   = 20f;   // Hz
    [SerializeField] float reconcileThreshold = 0.1f;  // m
    [SerializeField] float reconcileBlendTime = 0.1f;  // s
    [SerializeField] float snapThreshold      = 2f;    // m, 초과 시 즉시 스냅 + 로그
    [SerializeField] float interpolationDelay = 0.1f;  // s, 전송 간격의 2배로 시작

    public bool  PredictionEnabled      { get; }       // 비교 측정·시연용 토글
    public int   PendingInputCount      { get; }       // 진단
    public int   ReconcileCount         { get; }       // 진단
    public float LastCorrectionDistance { get; }       // 진단
}
```

> 수치는 전부 **측정 전 시작값**이다. 측정 후 조정하고 [STATUS.md](../STATUS.md)에 남긴다.
> **계약 자체는 조정 대상이 아니다.**

## 버퍼와 창 크기 — 시작값

`NetPlayerMotor`의 Inspector 값 외에 코드에 박히는 상한들이다. **전부 상한을 둔다.**

| 항목 | 시작값 | 없으면 |
|---|---|---|
| 서버 게임 틱 | **30Hz** (dt = 1/30) | — |
| 입력 history 버퍼 | **128틱** (약 4.3초) | 재조정할 때 되감을 기록이 없다 |
| 미래 입력 창 | **8틱** | 먼 미래 틱을 보내 서버 큐를 채울 수 있다 |
| 최근 입력 중복 전송 | **3틱** | 패킷 하나 잃으면 그 틱이 중립이 된다 |
| 서버 입력 큐 | **128틱** | 메모리가 무한히 는다 |
| 요청 결과 캐시 | **256개 / 연결** | 중복 요청 판별을 못 한다 |

> 캐시에서 지운 오래된 요청 ID도 **최고 처리 번호로 차단**해 재실행되지 않게 한다.

## `MoveInput.TargetTick`을 정하는 법

클라는 동기화된 서버 시간으로 **현재 서버 틱을 추정**하고, 거기에 **선행량 L**을 더해 배정한다.

```
TargetTick = 추정_서버_틱 + L

L의 시작값 = ceil( (RTT/2 + 지터여유 + 전송대기) / dt ) + 1
             → 2~8틱 범위에서 시작
```

**예:** 추정 서버 틱이 100이고 L=4면 입력을 104번 틱에 배정하고, 로컬은 그 틱까지 예측한다.
서버는 실제 104번 틱이 되었을 때 그 입력을 **한 번** 소비한다.

### L을 조정할 때

| 상황 | 처리 |
|---|---|
| L을 **줄일 때** | 같은 틱에 새 입력을 덮어쓰지 말고 **생성을 잠시 늦춘다** |
| L을 **늘릴 때** | 빈 틱은 **중립 입력으로 채운다** |
| 큰 시계 오차 · 백그라운드 복귀 · 버퍼 초과 | **예측을 중단하고** 새 기준 스냅샷으로 재동기화한다 |

`TargetTick`은 **단조 증가**시킨다.

**호스트는 네트워크 선행 없이 다음 서버 틱에 넣는다.**
서버 정지 후 누적 틱을 무제한 한 프레임에 실행하지 않도록 **catch-up 상한**을 두고,
초과 시 틱 원점을 재설정하고 이동 기준을 다시 배포한다.

## `MoveConfig`와 `MotionEpoch`를 지금 넣는 이유

둘 다 당장은 거의 비어 있지만, **나중에 넣으면 팀원 코드까지 깨진다.**
`.cs` 파일이 0개인 지금이 가장 싸다.

| 필드 | 없으면 생기는 일 |
|---|---|
| `MoveConfig` (스냅샷에 동봉) | 감속 디버프 후 클라가 옛 속도로 재생 → **보정 직후 다시 튀어나감** |
| `MotionEpoch` | 자동 부활 직후 **죽은 자리로 한 번 튕겼다 돌아옴** |
| 외력 슬롯 | 후순위 낚시바늘을 넣을 때 **이동 계약을 다시 깨야 함** |

# 2. 서버 계약

## 2.1 고정 스텝으로 소비한다

서버는 **고정 스텝**으로 입력 큐를 소비한다.
`input.DeltaTime`을 그대로 쓰지 않고 자신의 고정 스텝으로 대체하거나 상한으로 클램프한다.

## 2.2 틱당 한 번만 실행한다

**입력 패킷을 받을 때마다 `Step`을 호출하지 않는다.**
네트워크 콜백은 **큐만 채우고**, 서버 틱 실행기가 **틱당 한 번** 실행한다.

이걸 어기면 **전송량이 이동 속도를 결정한다** — 패킷을 많이 보내는 클라가 빨라진다.

## 2.3 유실된 틱은 중립 입력으로 확정한다

```
틱 T에서 Input[T]를 사용한다
  없으면 → 중립 입력으로 T를 완료한다
  뒤늦게 T가 도착해도 → 다시 실행하지 않는다
```

**왜 필요한가:** `seq`만으로는 "4번이 유실됐는데 5번이 왔다"에 답이 없다.
서버는 "마지막 걸 유지"하고 클라는 자기 히스토리로 재생하므로 **서로 다른 궤적이 나온다.**
손실 5% 환경에서 매 초 재조정이 터지는 형태로 나타난다.

**"마지막 수신 입력 번호"를 처리 완료 틱으로 대신 쓰지 않는다.**
중립 입력으로 확정한 틱도 처리 완료에 포함한다.

## 2.4 입력 검증

| 항목 | 처리 |
|---|---|
| `Seq` 역행 · 중복 | 버린다 |
| 지나치게 먼 미래 틱 | 버린다 |
| 이전 `MotionEpoch` | 거부한다 |
| `MoveDir` 유한성 · 크기 | 정규화하고 범위 검증 |
| `LookRot` 유한성 | 검증 |
| 연결별 수신 빈도 초과 | 버리고 로그 |

속도 상한 · 맵 경계 · 통과 불가 지형은 **`MoveStep` 안에서 서버가 강제한다.**

## 2.5 스냅샷

**`LastProcessedSeq`를 반드시 포함한다.** 이 값이 없으면 클라가 재조정 자체를 할 수 없다.

**`EffectiveConfig`를 같이 싣는다.** 따로 SyncVar로 보내면 도착 순서가 보장되지 않아,
최신 서버 디버프와 옛 클라 속도가 섞인다.

## 2.6 판정 좌표

**모든 거리·범위·상호작용 판정에 서버 시뮬레이션 좌표만 쓴다.**
클라가 보낸 좌표는 어떤 판정에도 쓰지 않는다.

지연 보상(되감기 판정)은 범위 밖이며, 채택하려면 별도 결정으로 올린다.

# 3. `MoveStep`의 결정론

**서버와 클라가 같은 계산을 하면 같은 결과가 나와야 한다.** 이게 예측의 전제다.

## 함수 안에서 쓰지 않는 것

```
난수
Time.time · Time.deltaTime · Time.realtimeSinceStartup
프레임률에 의존하는 값
물리 엔진의 비결정적 질의
```

## 구조

- 함수는 **이동 전용 위치**에 두고 서버·클라가 **같은 어셈블리의 같은 코드**를 참조한다
- **서버 전용 규칙을 클라 빌드에서 분기로 빼지 않는다**
- `kinematic Rigidbody`와 `Rigidbody.MovePosition`을 쓰더라도
  **결과를 만드는 계산은 `MoveStep` 한 곳에** 둔다

## kinematic 주의

**kinematic Rigidbody는 static 콜라이더와 부딪혀도 `OnCollisionEnter`가 오지 않는다.**

- **지형 충돌** → 이동 계산 안에서 `Physics.SphereCast` 등으로 직접 확인
- **트리거는 kinematic에서도 정상 동작**하므로 그대로 사용

단 이 질의가 결정성을 깨지 않도록 **서버·클라가 같은 콜라이더 상태를 보는 범위에서만** 쓴다.

→ 배경은 [LEARN/02_KINEMATIC.md](LEARN/02_KINEMATIC.md)

# 4. 클라 계약 — 예측

소유 클라는 입력을 보낸 **즉시** 로컬에서 같은 `MoveStep`을 적용해 화면을 갱신한다.

미확인 입력을 `Seq`와 함께 **상한 있는 버퍼**에 보관한다.
버퍼는 상한을 두고 초과 시 가장 오래된 것부터 버린다.

## 예측하는 것과 안 하는 것

```
예측한다      이동 축 · 회전 · 정적 지형과의 충돌
예측 안 한다   피격 · 포식 성공 · 성장 · 부활 완료
```

버튼 누름·입 벌리기 같은 **진행 중 표시는 로컬에서 먼저 보여도 되지만**,
성공 수치와 오브젝트 제거는 서버 확정 후에 반영한다.

# 5. 클라 계약 — 재조정

스냅샷을 받으면:

```
1. epoch 검증. 이전 MotionEpoch의 스냅샷은 버린다
2. LastProcessedSeq 이하를 버퍼에서 제거
3. 서버 상태와 "그 시점의 예측 기록"을 비교        ← 현재 위치가 아니다
4. 차이 > reconcileThreshold 면
      서버 상태로 되감고 → 남은 입력만 다시 Step
5. 차이를 reconcileBlendTime 동안 흡수             ← 매 프레임 스냅하지 않는다
```

`snapThreshold`(2m) 초과는 **즉시 스냅하고 로그를 남긴다.**
벽 관통 위험·순간이동은 시각 보간도 건너뛴다.

## 재시뮬레이션에서 하지 않는 것

**이동 계산만 다시 한다.**

```
포식 판정 · 피격 · RPC · 사운드 · 파티클 → 재발생시키지 않는다
```

## 이력이 부족할 때

`T`가 히스토리 범위를 벗어나거나 스냅샷이 로컬보다 앞서면 **억지로 재생하지 않는다.**
서버 기준 상태를 설치하고 시계·입력 범위를 다시 맞춘 뒤, **예측 끊김을 기록한다.**

# 6. 클라 계약 — 원격 보간

비소유 대상(원격 플레이어 · 서버 AI)은 스냅샷 버퍼를 두고
`NetworkTime.time - interpolationDelay` 시점을 보간해 표시한다.

```
렌더 시각을 둘러싼 스냅샷 A, B를 찾아
  alpha = (renderTime - A.time) / (B.time - A.time)
  위치는 Lerp, 회전은 Slerp
```

- 중복 시각은 제거하고, 순서 역전은 정렬 삽입한다
- **이미 표시한 시점보다 오래된 상태 때문에 시간을 뒤로 돌리지 않는다**
- 버퍼가 마르면 **짧게 외삽한 뒤 정지**한다. 무제한 외삽하지 않는다
- 스냅샷이 재개되면 **스냅 없이** 복귀한다
- 0.5초 이상 갱신이 없으면 연결 불안정 상태를 표시한다

## 절대 하지 않는 것

**원격 복제본에서 `MoveStep`을 다시 실행하지 않는다.**
남의 캐릭터를 내 PC가 다시 계산하면 서버와 어긋나 떨린다.

**클라 도착 간격으로 거리를 나누어 속도를 계산하지 않는다.**

## 시간축 함정

**RTT 지연을 보간 timeline에 두 번 적용하지 않는다.**
서버 시각 API와 보간 시각 API를 어댑터에서 구분한다.
현재 쓰는 API가 원시 서버 추정 시각인지 이미 지연된 timeline인지 **테스트로 확인한다.**

# 7. 행동 불능과 자동 부활

**HP 0 → 행동 불능 → 15초 뒤 서버가 자동 부활.**

```
행동 불능   서버는 입력을 계속 받되 이동에 반영하지 않는다
           서버는 상호작용을 거부한다
           클라는 예측을 중단하고 보간 표시로 넘어간다

부활        서버가 MotionEpoch를 올리고 기준 상태를 신뢰성 전송
           클라는 예측 버퍼와 보간 버퍼를 둘 다 비운 뒤 재개
           서버는 이전 epoch의 입력을 거부
```

> **전이 프레임에 예측 결과와 보간 결과가 동시에 Transform에 쓰지 않게 한다.**
> 여기가 떨림이 생기는 지점이다.

부활 시각은 **완료 시각 하나만 동기화**한다. 매 프레임 남은 시간을 보내지 않는다.

새 epoch의 이동 패킷이 기준 상태보다 먼저 오면 **제한된 버퍼에 보관**했다가 기준 상태 후 적용한다.

## 후순위 낚시바늘도 같은 규칙이다

바늘에 구속되면 예측을 중단하고 보간 표시로 넘어갔다가, 풀리면 버퍼를 비우고 재개한다.
**행동 불능과 완전히 같은 경로를 재사용한다.**

# 8. 진단

**이 세 값은 P03의 산출물이지 나중에 붙이는 편의 기능이 아니다.**
없으면 T17·T18을 눈으로만 판단하게 된다.

```
PendingInputCount        미확인 입력 수
ReconcileCount           재조정 발생 횟수
LastCorrectionDistance   마지막 보정 거리
```

## 진단 HUD 항목

P03~P04에서 화면에 띄워 두면 문제를 눈으로 잡을 수 있다. **P09에서 정식화한다.**

```
RTT · jitter                    네트워크 상태
serverTick · predictedTick      둘의 차이가 곧 선행량 L
input lead                      현재 L 값
ACK age                         마지막 스냅샷을 받은 지 얼마나 됐나
prediction error                보정 전 오차
correction count                재조정 횟수
snapshot buffer depth           보간 버퍼가 마르고 있나
motionEpoch                     부활·순간이동 이력
bytes/s                         전송량
```

로그에는 `session / tick / actor / target / request / revision / result`를 남긴다.

> **같은 스냅샷 revision끼리 비교한다.**
> 서로 다른 시각의 화면 위치를 불일치로 판정하지 않는다 — 보간 지연 때문에 당연히 다르다.

추가로 남길 것: 스냅 발생 여부, 보간 버퍼 고갈 횟수.

## `PredictionEnabled`

예측 유무 **비교 측정과 시연 영상**을 위한 토글이다.
기본값은 켜짐이며, **꺼진 상태를 정상 플레이 경로로 인계하지 않는다.**

# 9. 호스트 경로

호스트의 로컬 플레이어는 서버와 같은 프로세스이므로 **예측·재조정 경로가 실질적으로 비어 있다.**

```
호스트에서 테스트      → 전부 잘 돼 보인다        ← 함정
원격 Client에서 테스트  → 여기서 진짜가 드러난다
```

**T16~T19는 반드시 원격 Client에서 판정한다.**

호스트 입력은 네트워크 선행 없이 다음 서버 틱에 넣는다. 서버 모터만 실행하며
화면은 프레임 사이를 부드럽게 표시한다.

호스트는 서버 게임 로직과 클라이언트 표현 경로를 **분리한다** —
HP·AI·VFX를 두 번 처리하지 않도록 한 경로로만 실행한다.

# 10. 자주 터지는 곳

| 증상 | 원인 | 확인 |
|---|---|---|
| 캐릭터가 계속 튄다 | **서버와 클라의 `MoveStep`이 다르다** | 임계값을 만지기 전에 이것부터 의심 |
| 보정 직후 다시 튀어나간다 | `MoveConfig`를 스냅샷에 안 실었다 | 별도 SyncVar로 보내고 있는지 |
| 손실 환경에서 재조정 폭발 | 유실 틱을 중립으로 확정 안 함 | 2.3절 |
| 부활 직후 죽은 자리로 튕김 | `MotionEpoch` 없음 또는 버퍼 안 비움 | 7절 |
| 패킷 많이 보내면 빨라짐 | 패킷마다 `Step` 호출 | 2.2절 |
| 원격이 떨린다 | 원격에서 `MoveStep` 재실행 | 프로파일로 확인 |
| 원격이 계속 늦다 | RTT를 보간 timeline에 두 번 적용 | 6절 시간축 |
| 호스트만 잘 된다 | 원격에서 테스트를 안 했다 | 9절 |

# 11. 수치 변경 기록


이동 계약을 바꿔야 하면 **T16~T19를 다시 돌린 뒤** 커밋한다.
